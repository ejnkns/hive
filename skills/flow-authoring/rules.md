## Rules that make generated flows actually work

- Every `ai-task` and `ai-chat` declares a `systemPrompt` that names the job and the completion tool to call. A prompt-less agent produces prose instead of structured output, or the runner fails fast.
- When an ai-task must return data, declare `completionOutput` with exactly the fields the flow records — the only output an ai-task can carry is its completion-tool arguments.
- Record structured output with a sibling operation `patch` task that copies `output.<field>` into instanceState, and gate its `taskError` into a retry/needs-review state. A patch op fails when a sourced value is missing, so that state is mandatory, not optional.
- Every instance-state field shown by `instance`/`display` hints has a writer: a patch op, an edge field, a createInstance payload key, an engine op, or a cross-instance write declared in an op's `writesAcross`. An instance that displays a field nothing writes is a broken card.
- A cross-instance write (E1) is same-flow only and always declared: an operation that patches a sibling instance via `ctx.patchInstanceState(instanceId, patch)` declares the target workflow and fields in its `writesAcross` — the module-set gate rejects a sibling patch the operation does not declare, and the validator checks the fields against the target workflow's instanceState. Unknown instance ids return false (the op handles a stale reference); undeclared patch keys throw into the flow's needs-review state.
- The cross-instance query `workflowInstancesInState(workflowId?, stateId?)` returns every instance with its `workflowId`; filter by workflow and/or state positionally (`"ideas"` for every ideas instance, `(undefined, "done")` for every done instance). Resolve a title to an id through it before patching a sibling by title.
- Instance deletion is a destructive action flag, never a transition: a `deletesInstance: true` action (destructive variant, no transitionTo) removes the instance when it fires — the engine drops the controller, deletes its persisted state, and the board loses the card. References to a deleted instance go stale gracefully (a missing id is an unmet dependency, never an error), so a `Discard`/`Delete` action needs no retry state.
- Board grouping by field value is a generic partition: `ui.groupByField` names a declared instance-state field and the board renders one column per distinct value (plus Uncategorized for empties) — the engine never interprets values (no labels, ordering, or semantics); map values to labels in display hints if you want them labeled.
- A `flowComponent` names a served component id declared in `ui.components`; an undeclared id is an advisory (the page body falls back to the default surface). The flow component owns the WHOLE page body — the shell keeps only the breadcrumb and a manage/delete affordance, which a served module never receives (delete/status/identity are not in `FlowViewProps`).
- A served component module composes only DEFAULT elements by tag (`<workflow-board-content>`, `<markdown-view>`, `<chat-session>`): served modules are registered under generated tags, so one served module cannot reference another served module's component id as a tag. Put per-workflow custom cards in `instanceComponent` (resolved through the registry) and compose the canonical board with `<workflow-board-content>`.
- Declared persisted outputs (`ui.persistedOutputs` / `ui.persistedOutputDirs`) name domain files under `domainDir` only — the server reads them through the engine's persisted-output seam and ships their contents in the snapshot. Declare only what the UI actually renders; an escaping path degrades to empty.
- Cross-entity data lives in flowState, never duplicated on instances: declare `flowState` fields (field + type), write them from operations via `ctx.patchFlowState(patch)` (mirrors patchFlowConfig), read them from operations and tools via `ctx.flowState()`. FlowState writes are validated like instance writes — the gate rejects an undeclared patchFlowState key, the validator rejects an undeclared toFlowState edge transform field. Per-idea classifications are instance data on the cards, not flowState.
- AI-derived values drive the edit UI through runtime options: an edit field declares `optionsFrom: { flowState: "path.to.values" }` (first segment a declared flowState field; mutually exclusive with static `options`); the server resolves it to a select's options from flowState, and the field degrades to free text when the source is absent — so a category field offers the taxonomy's categories, never a hardcoded list.
- Every created instance receives its seed data. Required createInstance fields reject empty values, and auto tasks seed their input from instanceState — so give each new instance the field its first task reads.
- A task's completion tool is offered automatically; list only infrastructure tools explicitly in `tools`.
- Every workflow with fallible tasks has a way out: a needs-review/error state with a retry action. An instance that can never leave a running state is a zombie.
- Design the whole lifecycle before writing the spec: which states exist, which are reachable from `initial`, which transitions fire under which gate, which terminals finish. A state nothing reaches, or that cannot leave, is a design flaw the check flags.
- Implement a referenced file by keeping the export name and contract the reference derives (gates/transforms/extracts/prompts export the camel-cased file base name; tools export <id>Tools; operations export <id>Operations) — the gate checks the exact name. A renamed or mis-typed export fails the lint with a specific finding.
- Hand edits to referenced files are authoritative — validation never overwrites a file you wrote. Implement the referenced export, then validate again to run the gate against it.
- Declare every external package a referenced file imports in the definition's `dependencies`. Imports are limited to engine primitives (workflow-engine/*), the flow's own files, `node:` builtins, and declared packages; anything else fails the gate with a readable finding.
- Never use `any` in a referenced module — the gate rejects it. Use `unknown`, `Record<string, unknown>`, or the flow's own state type bound once per group (`defineOperations<TState>` / `defineTool<TState>`); `any` disables the typecheck that catches wrong-receiver state access (`task.` instead of `ctx.`).
- Keep a gate transition in a state whose tasks are all complete before the gate runs — auto-transitions evaluate after each task, so a gate sharing a state with an earlier task fires too early (a file gate reading a field an extractor writes must live in the state after the extractor).
- Type a referenced gate with the flow's own state types: `GateContract<IdeaState, FlowState>` (defaults keep an un-annotated gate working). Instance and flowState fields become typed — no casts. Keep fields optional and guard with `??`/`?.`: a field is genuinely undefined until its writer runs, and a gate that reads it too early must say "no", not crash.
- A gate that throws evaluates as false (fail-safe): the engine treats an un-evaluable gate as "the condition is not met" — it never errors the completing task or breaks the snapshot. Since the module-set typecheck catches typo'd field names, a runtime throw means a field was read before it was written.
